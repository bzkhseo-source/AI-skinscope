# 성분 추천 상품 링크 개선 (식약처 데이터 조사 및 네이버쇼핑 API 전환)

작성일: 2026-10-14

## 0. 배경 — 문제 상황

성분 추천 카드의 "관련 화장품 검색 →" 링크는 네이버쇼핑 통합검색에
"{성분명} 성분 화장품 인체용 -강아지 ..." 형태의 키워드만 던지는 방식이었다
(`app/services/ingredient_service.py`의 `_build_search_url()`). 실사용
확인 결과, 해당 성분이 들어간 **완제품**이 아니라 그 성분 자체를 원료로
파는 **원료/벌크 판매 상품**이 검색 결과에 섞여 나오는 사례가 보고되었다
(예: "바쿠치올" 검색 시 원료 공급처 상품 노출).

## 1. 식약처(식의약 데이터 포털) 등 공공데이터 활용 가능성 조사

"성분명을 넣으면 그 성분이 든 시중 유통 완제품 목록이 나오는" 공식 정부
데이터 소스가 있는지 조사했다.

**핵심 제약 — 법원 판결로 막힌 "성분→제품" 역조회**: 2017년 서울행정법원
(2016구합81826)이 아모레퍼시픽 등 화장품사 19곳이 식약처를 상대로 낸
소송에서 회사 측 손을 들어줬다. 소비자가 식약처에 "화장품별 원료 목록"
정보공개를 청구했다가 거부당해 제기한 소송으로, 법원은 품목별 전성분
데이터를 **영업상 비밀**로 인정했다 — 18만여 품목의 원료 데이터가 공개되면
경쟁사가 배합 경향을 파악해 유사 제품을 만들 수 있다는 논리였다. 즉 식약처가
보유한 품목별 전성분 DB를 공공데이터로 공개받는 경로는 이 판례로 사실상
막혀 있다.

`data.mfds.go.kr`(식의약 데이터 포털)과 `data.go.kr`에 "화장품 원료성분정보",
"화장품 사용제한 원료정보", "화장품 관련 정보" 등 화장품 카테고리 데이터셋이
있으나, 상세 페이지는 접근이 제한되어 있었고 명칭과 위 판례로 미루어보면
원료 자체의 사전적 정보(배합목적·사용한도·네거티브리스트)이지 "품목명 +
전성분" 형태의 제품별 매핑은 아닌 것으로 판단된다.

유사 서비스("유사 화장품 추천" 프로젝트, velog 개발기)의 실제 사례도 이를
뒷받침한다 — 해당 개발자도 식약처 API는 쓰지 않았고, 성분명 표준화에는
대한화장품협회 성분사전(kcia.or.kr, 크롤링)을, "제품명 + 전성분" 매핑에는
국내 공공데이터가 아니라 해외 사이트 INCIDecoder.com을 크롤링했다.

## 2. 화해(hwahae.co.kr) 검토

사용자 요청으로 화해(국내 대표 뷰티 앱)도 대안으로 검토했다.

- **제공 기능**: 화해 앱 설명("내가 찾는 모든 화장품의 성분 확인")과
  릴리즈노트("좋아하는 제품과 성분이 가장 비슷한 제품을 지금 확인해
  보세요")로 볼 때, 화해의 성분 기능은 **제품 → 그 제품의 성분 확인**과
  **제품 → 성분이 비슷한 다른 제품 추천**(제품 대 제품 비교)이다.
  **성분명 → 그 성분이 든 제품 목록**이라는 역방향 검색은 앱 설명에
  언급되지 않았고, 사이트 자체 검색(`/search`)도 일반 인기 제품 목록만
  보여줄 뿐 성분 기반 필터로 보이지 않았다.
- **API/제휴**: 공개된 Open API나 제휴 프로그램 안내는 확인되지 않았다.
  "광고/제휴문의"(business.hwahae.co.kr)로 개별 문의가 필요한 구조다.
- **결론**: 화해는 "성분→제품" 역방향 검색을 공식 기능으로 제공하지
  않고, 공개 API도 없어 이번 개선의 데이터 소스로 바로 쓸 수 없다. 다만
  "제품 상세 화면에 성분을 투명하게 보여준다"는 UX 방향 자체는
  AI-SkinScope의 성분 추천 카드 설계와 결이 같아 참고할 만하다.

## 3. 의사결정 — 네이버쇼핑 검색 API 기반 완제품 필터링 채택

공식 정부/업계 데이터로 "성분→제품" 역조회를 대체할 방법이 없으므로,
기존에 쓰던 네이버쇼핑을 **링크 생성이 아니라 서버사이드 API 호출**로
바꿔 결과를 필터링하는 방식을 택했다.

- 네이버쇼핑 검색 API(`openapi.naver.com/v1/search/shop.json`)로
  "{성분명} 성분 화장품"을 검색해 상위 20건을 받는다.
- 상품명에 원료 판매 특유 키워드(원료/벌크/대용량/비누베이스/공방/소분/
  DIY/캐리어오일 등)가 있으면 제외한다.
- 응답의 `category1`이 존재하는데 "화장품/미용"(네이버 쇼핑 분류체계
  대분류, 쇼핑인사이트 API 기준 코드 50000002와 동일 체계)이 아니면
  제외한다. 단, 필드가 비어있거나 예상과 다른 응답이어도 관대하게
  통과시켜 분류체계 변경에 전체 기능이 깨지지 않도록 했다.
- 위 필터를 통과한 첫 번째 결과의 실제 상품 링크(`item.link`)를 쓴다.
- API 키 미설정, 네트워크/응답 오류, 적합한 결과 없음 등 어떤 이유로든
  실패하면 기존 범용 검색 링크(`search.shopping.naver.com`)로
  degrade한다 — 장애 허용 원칙(기술적용 매뉴얼 9장)과 동일하게
  적용했다.

## 4. 구현 요약

- `app/services/naver_service.py` (신규): `find_cosmetic_product_url()`.
  성분 카탈로그가 유한(고민 8종 x 상위 5개 이내, 최대 수십 개)해 프로세스
  생존 기간 동안 메모리 캐시(`_search_cache`)로 중복 API 호출을 없앴다.
  타임아웃은 1.5초로 짧게 잡아, API 장애 시에도 한 번의 분석 요청(성분
  최대 10개)에서 응답 지연이 과도하게 누적되지 않도록 했다.
- `app/services/ingredient_service.py`: `_resolve_search_url()`을
  추가해 `naver_service.find_cosmetic_product_url()`을 먼저 시도하고,
  `None`이면 기존 `_build_search_url()`(범용 검색 링크)로 대체한다.
- `app/core/config.py`: `naver_client_id`/`naver_client_secret` 설정
  추가(기본값 빈 문자열 — 미설정 시 자동 degrade, kakao/uv 키와 동일
  패턴).
- `app/schemas/agent.py`: `IngredientRecommendation.search_url`의
  설명을 "범용 검색 링크"에서 "실제 상품 링크 우선, 없으면 범용 검색
  링크로 대체"로 갱신.
- `.env.example`/`README.md`: `NAVER_CLIENT_ID`/`NAVER_CLIENT_SECRET`
  안내 추가(developers.naver.com에서 무료 발급, 선택 항목).

## 5. 알려진 한계

- `category1` 필드명·값("화장품/미용")은 네이버 쇼핑 분류체계 공개 자료를
  근거로 했으나, 실제 검색 API 응답에서 직접 확인하지는 못했다. 필터가
  관대한 기본값(필드 없으면 통과)으로 설계되어 있어, 설령 값이 다르더라도
  전체 기능이 깨지지 않고 "필터링 효과가 약해지는" 수준으로 degrade된다.
- API 키 미발급 상태에서는 기존과 동일하게 범용 검색 링크만 제공된다 —
  이 개선의 효과를 보려면 `NAVER_CLIENT_ID`/`NAVER_CLIENT_SECRET` 발급과
  배포 환경(Render) 환경변수 등록이 필요하다.
- 네이버쇼핑에 등록되지 않았거나 상품명에 성분명이 직접 노출되지 않는
  제품은 여전히 걸러지지 않는다 — "성분→제품"의 완전한 역조회가 아니라,
  "텍스트 검색 결과 중 원료성 상품을 골라내는" 수준의 개선이다.
