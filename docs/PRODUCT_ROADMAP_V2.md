## 1. 기능별 기술 설계

### A. 카메라 좌우 반전(미러링) 수정 — 난이도: 낮음

**현상**: 전면 카메라 사용 시 미리보기 화면이 실제 거울처럼 안 보이고
좌우가 뒤집힌 채로 보여 어색함.

**원인**: `<video>` 요소 자체는 CSS 변형이 없어 카메라 원본 그대로 표시됨.
셀카 카메라는 통상 "거울처럼" 보여야 자연스러움.

**설계**:
- `state.facingMode === "user"`일 때만 `<video>` 요소에 CSS
  `transform: scaleX(-1)` 적용 (실시간 미리보기만 좌우반전)
- 실제 촬영 로직(`capturePhotoFromVideo`)은 이미 캔버스 레벨에서 별도로
  좌우보정을 하고 있으므로 그대로 유지 (CSS 변형은 캔버스 `drawImage`에
  영향 없음 — 저장되는 사진 방향은 변화 없음)
- 후면 카메라는 반전 없이 그대로 유지

---

### B. 촬영 가이드 (정적 오버레이) — 난이도: 낮음

**설계**:
- 뷰파인더 중앙에 반투명 타원형 얼굴 가이드라인 SVG 오버레이 추가
- 가이드 위/아래에 짧은 안내문구: "타원 안에 얼굴을 맞춰주세요 (정면, 밝은 곳)"
- 최초 1회, 동의 화면 통과 직후 촬영 팁 툴팁을 3초간 노출 (선택)

---

### C. 얼굴 정렬 확인 + 조건 충족 시 자동 촬영 — 난이도: 높음

**설계**:
- 브라우저 내장 `FaceDetector` API가 있으면 사용(Chrome 계열 일부 지원),
  없으면 `@mediapipe/face_detection`(CDN, TF.js 기반)을 폴백으로 로드
- 매 200~300ms 간격으로 비디오 프레임에서 얼굴 바운딩박스 검출
- "가이드 타원 안에 얼굴이 일정 비율 이상 들어오고, 흔들림이 적은 상태"가
  약 1초 지속되면 자동으로 `capturePhotoFromVideo()` 호출
- 감지 실패/미지원 브라우저에서는 기존 수동 셔터 버튼으로 자연스럽게 대체
  (progressive enhancement — 필수 아님, 있으면 좋은 기능)
- **참고**: 이 기능은 클라이언트 사이드 연산 부담이 있어 저사양 기기에서
  버벅임 가능성 있음 → 실기기 테스트 필요

**진행 현황 (2026-08-27 업데이트)**: 구현 완료, **실제 브라우저 검증 필요**.
`FaceDetector`는 브라우저 지원이 매우 제한적/축소 추세라 있으면 우선 사용하고,
없으면 (레거시 `@mediapipe/face_detection` 대신) 현재 유지보수되는
`@mediapipe/tasks-vision`을 CDN(jsdelivr)에서 동적 import로 로드하는 방식으로
구현했다. 이 프로젝트는 번들러가 없어 CDN 로드가 유일하게 실용적인 방법이다.
가이드 타원 대비 얼굴 박스 크기·중심 거리로 정위치 여부를 판단하고, 1초 이상
유지되면 자동 촬영한다. 감지 초기화 실패(네트워크 차단 등)는 catch로 흡수해
기존 수동 셔터로 조용히 대체된다. **다만 실제 카메라가 있는 브라우저 환경에서
직접 눈으로 확인하지 못했다** — CDN 모델 로딩, 좌표 변환, 저사양 기기 버벅임
여부는 실기기 테스트가 필요하다.

### D. 결과 공유 기능 — 난이도: 낮음

**설계**:

  (개인정보 보호 원칙 유지)

### E. "진단 아님" 문구 노출 최소화 — 난이도: 낮음

**현재 문제**: 결과 화면 여러 섹션에 유사 문구가 반복되어 신뢰도가
떨어져 보임(user_8dfkmr15 피드백).

**설계**:
- 결과 화면 상단에 **1회만, 눈에 띄게** 고지 (기존 disclaimer 카드 유지)
- 나머지 섹션(참고 패턴, 관리팁 등)에서는 문구 반복 제거
- 대신 하단에 "이 결과는 어떻게 만들어지나요?" 접이식(collapsible) 섹션을
  추가해 근거(멀티모달 분석 + RAG 근접사례 + 인구통계 anchor)를
  간단히 설명 → "신뢰도를 낮추는 반복 경고" 대신 "근거를 보여주는 투명성"으로 전환

### F. AI 소견 구조화 — 난이도: 낮음~중간

**현재 문제**: `ai_summary`가 자유서술형 한 단락이라 "병원 가라"는
말만 반복되는 느낌(user_hm5ijs63 피드백).

**설계 (스키마 변경)**:
`SkinAnalysisResult`에 필드 추가:
```python
key_finding: str       # 핵심 소견 한 줄 (예: "T존 모공 확장이 두드러집니다")
comparison_note: str   # 동년배/인구 평균 대비 설명 (G 항목과 연동)
action_items: List[str]  # 구체적 관리 행동 제안 (기존 care_tips와 통합 검토)
```
- 프롬프트에 "병원 방문 필요성만 말하지 말고, 반드시 관찰된 구체적 특징을
  1문장으로 먼저 제시하라"는 지침 추가
- 프론트: AI 소견 섹션을 "핵심 소견 → 동년배 비교 → 관리 제안" 3단 구조로 표시

### G. 나이·성별 입력 + 동년배 비교 + 피부나이 — 난이도: 중간

**설계**:
1. 촬영 화면에 나이(숫자)·성별(선택, 선택안함 가능) 입력 필드 추가 —
   `/analyze` 요청에 `age`, `gender` 파라미터로 전달 (선택 입력, 필수 아님)
2. **동년배 비교**: `measurement_data.csv` 전체(1,072명)를 나이대(10년 단위)
   ×성별로 그룹핑해 그룹별 백분위 재계산 → 사용자가 나이를 입력하면
   전체 인구 anchor 대신 해당 그룹 anchor를 프롬프트에 사용
3. **피부나이 산출**: 사용자의 6개 feature_score를 각 연령대 그룹의 평균
   프로파일과 비교해, 가장 가까운(유클리드 거리 최소) 연령대의 대표 나이를
   "피부나이"로 제시 (실제 나이와 함께 "피부나이 24세" 형태로 노출)
4. 나이 미입력 시 기존처럼 전체 인구 anchor 사용 (하위 호환)

**진행 현황 (2026-08-27 업데이트)**: 완료.
`scripts/build_age_gender_reference.py`가 `meta_data.csv`(나이·성별)와
`measurement_data.csv`(실측값)를 subject_no로 조인해 연령대(10년 단위)×성별
그룹별 백분위(`app/data/age_gender_reference.json`)를 만든다. 12개 연령대×성별
그룹 모두 표본이 충분해(최소 51명) fallback 없이 전부 사용 가능했다.
`vision_service.py`의 `_build_dynamic_population_text()`가 나이 입력 시 이
그룹 anchor로 프롬프트를 대체하고, `compute_skin_age()`가 사용자 feature_scores와
가장 가까운 연령대를 유클리드 거리로 찾아 피부나이를 산출한다. 동년배 비교
문구(`peer_comparison_note`)는 Gemini를 다시 호출하지 않고 사전 집계된 통계만으로
결정론적으로 생성해 비용을 늘리지 않았다. `skin_records` 테이블에는 Alembic 없이
가벼운 startup 마이그레이션(`app/main.py`)으로 `age`/`gender`/`skin_age` 컬럼을
추가해, 기존에 저장된 실사용자 테스트 기록도 깨지지 않고 그대로 유지된다.

### H. 부위별(T존/이마/코/볼/턱) 세분화 분석 — 난이도: 높음

**설계**:
- `SkinFeatureScores`를 부위별 중첩 구조로 확장(하위 호환 위해 기존
  전체 점수는 유지하고 `regional_scores` 필드 추가):
```python
regional_scores: Dict[str, RegionScore]  # key: "forehead","nose","cheek_l","cheek_r","chin"
```
- 프롬프트에 "얼굴을 이마/코(T존)/양볼/턱 5개 구역으로 나누어 각 구역별로
  모공·유분·트러블 정도를 관찰하라" 지침 추가
- **근거**: 이미 우리가 만든 실측 RAG 인덱스가 `facepart`(0~6, 부위별)
  단위로 측정값을 가지고 있으므로, 부위별 anchor도 동일한 방식으로 산출 가능
- 프론트: 결과 화면에 얼굴 다이어그램(SVG) 위에 부위별 배지로 시각화

**진행 현황 (2026-08-27 업데이트)**: 완료. `SkinFeatureScores`(기존
6개 항목)는 그대로 두고, `SkinAnalysisResult`에 `regional_scores`
(`Optional[RegionalScores]`, 5개 부위를 각각 명시적 필드로 선언 — Gemini
구조화 출력의 안정성을 위해 로드맵 원안의 `Dict[str, RegionScore]` 대신
고정 필드 방식을 채택)를 추가했다. `scripts/build_region_reference.py`로
`measurement_data.csv`의 부위별 실측 컬럼(이마/왼쪽볼/오른쪽볼/턱의 수분·탄력,
볼의 모공 개수)을 그대로 사용해 부위별 백분위(`app/data/region_reference.json`)를
만들었다. **다만 실제 데이터를 확인한 결과 "코(T존)"에 대응하는 장비 실측치는
이 데이터셋에 전혀 없다**(스마트폰 촬영 라벨의 facepart 2/7번 슬롯이 60명
표본 전원에서 equipment=None으로 확인됨) — 코 부위는 실측 anchor 없이
Gemini의 시각적 판단만으로 평가하며, 이는 기존 "붉은기" 항목과 동일한 처리
방식이다. 프론트엔드에는 5개 점(이마/코/양볼/턱)이 있는 간단한 얼굴 SVG
다이어그램과 부위별 노트 목록을 추가했다.

### I. 제품 성분 추천 — 난이도: 중간~높음 (전체 데이터 분석)

**데이터**: AI Hub "스킨케어 성분-효능 추천 데이터" (7.17GB, 텍스트+이미지,
LMM 생성, 내국인 신청 가능)

**설계**:
1. 데이터 다운로드 후 구조 확인 필요 (STEP 4 때처럼 폴더 트리 확인)
2. **전체 데이터 분석**(샘플링 아님)으로 진행:
   - 성분별 효능 텍스트를 `gemini-embedding-2`로 임베딩 → 별도 참고
     인덱스(`reference_ingredients.json`) 생성
   - 대량 데이터라 배치 처리 + 중간 저장(재시작 가능한 구조는 기존
     `build_reference_embeddings.py`와 동일한 패턴 재사용)
3. 실시간 분석 시: 사용자의 `feature_scores`(모공·수분·주름 등 취약 항목)를
   기준으로 관련성 높은 성분을 임베딩 유사도로 검색 → `recommended_ingredients`
   필드로 응답에 포함
4. **판매사이트 연결**: 실제 커머스 API 연동은 범위 밖으로 제외하고,
   "네이버쇼핑에서 '나이아신아마이드 세럼' 검색" 형태의 **검색 링크**로 대체
   (실시간 재고·가격 연동 없이, URL 파라미터로 검색어만 전달)

**진행 현황 (2026-08-27 업데이트)**:
- 항목 I는 `scripts/build_ingredient_map.py`(텍스트 코퍼스 전수분석 +
  concern별 랭킹, 임베딩 유사도 검색이 아닌 언급빈도/특이도 기반 방식으로
  1차 구현)로 데이터 준비를 마쳤다. 상세 방법론과 발견된 이슈(성분
  차별화 부족 → specificity/lift 스코어링으로 해결)는
  `docs/INGREDIENT_SPECIFICITY_SPEC.md` 참고.
- `app/services/ingredient_service.py`가 `vision.feature_scores` 기준
  가장 취약한 1~2개 고민 카테고리를 골라 `AgentResult.product_recommendations`
  필드(검색 링크 포함)로 응답에 포함하도록 연동 완료. 프론트엔드 결과
  화면에 "추천 성분" 카드로 노출된다.
- 위 3번 항목("임베딩 유사도로 검색")은 채택하지 않고, 텍스트 코퍼스에서
  추출한 concern별 specificity 랭킹 방식으로 대체했다 — 실시간 임베딩
  검색 인프라 없이도 사전 계산된 JSON 조회만으로 충분히 차별화된 추천이
  가능했기 때문.
